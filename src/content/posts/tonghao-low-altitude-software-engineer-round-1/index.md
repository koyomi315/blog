面试日期：10 月 15 日。面试结果：未记录。

这篇面经根据我本人的回答转写整理，问题由回答推断，并经我核对修正。主要围绕实习中的 Agent 评测平台展开，随后问到了 Redis 和 Java 相关基础。

## 一、自我介绍与技术背景

1. 请做一下自我介绍。
   - 当时回答：主要方向是 Java 后端和 Agent 应用开发。介绍了滴滴实习中的自动定时评测与 Tool Mock 工作，以及运维 Agent、高并发秒杀两个个人项目。自我介绍中提到，两项实习工作完成了验收上线。
2. 你主要使用 Java 还是 Go？Go 是什么时候接触的？
   - 当时回答：主要使用 Java，Go 是实习期间因工作需要才开始学习的。

## 二、实习项目与异步任务

3. 选择一段熟悉的项目经历，介绍背景和要解决的问题。
   - 当时回答：选择实习中的 Agent 评测平台。评测对象是指引外卖商家入驻的业务 Agent，平台一方面评估线上表现、挖掘问题，另一方面检查 Agent 升级后的能力变化和回归情况。
4. 自动定时评测的异步任务如何运行？遇到了哪些难点，如何处理？
   - 当时回答：外部定时平台每分钟触发接口，扫描到期配置并创建任务，串联 Trace 收集、评分和低分 Bad Case 归集。
   - 幂等方面，用任务 ID 与执行时间构成联合唯一索引，避免同一个执行时点重复创建任务。
   - 并发方面，通过消息队列派发任务，Worker 申领时按预期状态做 CAS 更新，同时记录领取者并更新状态。
   - 异常方面，定时检查任务，对部分异常重新派发，对无法推进的任务收敛为失败，避免一直停留在执行中。
5. 追问：异步任务处理这一块是怎么做的？
   - 当时回答：补充说明了类似轮询的触发方式，外部平台在整分钟调用指定接口，再由接口推进后续扫描和异常处理。
6. 追问：外部定时平台具体负责什么？每分钟触发后，你的服务做什么？
   - 当时回答：外部平台类似信号源，定期触发接口；任务扫描和异常状态归集等逻辑在服务内处理。
7. 追问：定时平台正常情况下会重复触发吗？为什么还需要幂等设计？
   - 当时回答：认为外部平台没有问题时理论上不会重复触发，幂等主要是设计时的防御性考虑。
8. 异步任务主要通过什么机制派发？
   - 当时回答：主要通过消息队列。
9. 追问：使用 CAS 后，真实业务中多个 Worker 争夺同一个任务，就确实没有问题了吗？
   - 当时回答：一个 Worker 领取后，没有观测到其他 Worker 继续竞争同一任务的情况。当时主要依据实际观察作答，没有进一步完整论证方案在各种并发场景下是否充分。
10. 开发或测试中还遇到过什么具体问题？
    - 当时回答：本机代码更新后，新任务可能被同事电脑上未更新的旧 Worker 领取。旧 Worker 无法处理新任务，导致任务失败。

## 三、平台部署与异常恢复

11. 你的评测平台是怎么部署上线的？
    - 当时回答：平台和 Worker 通过 Docker 部署到服务器，供内部验收和使用。上线有工作流，相关部署会较快地逐个更新。
12. 追问：逐个更新期间，旧 Worker 仍可能领到新任务吗？
    - 当时回答：起初认为线上统一更新就能解决，但进一步讨论后承认，更新过程中也可能出现旧 Worker 领取新任务的情况。随后补充系统主要供内部研发使用，使用人数还不多；没有给出进一步的兼容处理方案。
13. 任务状态存放在哪里？
    - 当时回答：任务及其状态都保存在数据库中。
14. 追问：长时间卡住的任务如何处理？哪些可以重新投递，哪些收敛为失败？
    - 当时回答：检查长时间没有推进的任务，将部分任务收敛为失败，有些情况可以重新投递。提到了 10 分钟或 30 分钟等时间，但没有清楚说明各自对应的状态和处理条件。

## 四、Redis 使用与单线程

15. 用过 Redis 吗？消息队列用的是什么？Redis 用在哪些场景？
    - 当时回答：公司使用内部消息队列。Redis 主要是在学习高并发秒杀项目时使用，作为相关知识的实践。
16. 你如何理解 Redis 的单线程？项目中如何利用这个特性？
    - 当时回答：理解为命令串行执行。项目中使用 Lua 脚本，把整个脚本理解为统一的一条指令，以此说明脚本内多个操作的原子性。
17. 继续追问：你是怎么理解 Redis 的单线程的？
    - 当时回答：对 Redis 底层是否只有一个线程并不特别了解；顺着讨论表示，如果只有一个线程执行计算，相比多线程，计算能力可能受到限制。当时没有进一步解释清楚线程模型。

## 五、事务注解与锁升级

18. 你了解 Spring Boot 的事务注解吗？
    - 当时回答：提到了 transaction，并用“要么全部成功，要么全部失败”解释原子性。随后又说事务注解不能保证外部数据库操作的原子性，并尝试区分程序内部计算与外部数据库操作，但这部分没有解释清楚。
    - 这里保留当时的回答，不作为事务机制的参考说明。
19. 了解 synchronized 的锁升级吗？各阶段有什么区别，为什么要升级？
    - 当时回答：按无锁、偏向锁、轻量级锁、重量级锁展开。认为偏向锁对应只有一个线程使用，轻量级锁对应竞争不激烈时通过 CAS 获取，重量级锁对应竞争激烈时阻塞未获取锁的线程，减少大量无效 CAS 对计算资源的占用。
    - 当时没有结合具体 JDK 版本展开讨论。

## 七、面试复盘：整理建议

以下是根据本场记录补充的事后建议：

- **异步任务：** 把定时触发、任务投递、领取执行和异常恢复分开说明，准备一个具体的任务状态变化示例。对于 CAS 的追问，不能只依靠“没有观测到问题”作答。
- **部署与恢复：** 复盘新旧 Worker 混用的问题，说明自己当时实际做了什么、哪些情况尚未覆盖；把超时阈值、适用状态和重投条件说清楚。
- **技术基础：** 重点回看 Redis 单线程的含义、事务注解的作用范围，以及特定 JDK 版本中的锁机制，避免只记住概念名称而无法解释边界。
