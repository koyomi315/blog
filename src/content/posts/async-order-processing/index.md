将下单逻辑放到消息队列后，接口可以更快返回，数据库也能够按可控速度处理订单。但异步化只是把时间从请求线程移到了后台，并没有让失败消失。

## 同步链路与异步链路的边界

同步入口通常只完成：

1. 校验并扣减快速库存；
2. 生成全局唯一订单 ID；
3. 投递下单消息；
4. 返回“已受理”。

消费者再完成数据库条件扣库存、写订单和其他后续动作。

此时客户端拿到的不是“订单已经持久化”，而是“系统接受了请求”。接口语义需要明确，否则用户会把短暂查询不到订单理解为失败并重复提交。

## 生产消息可能失败

如果 Redis 资格已经扣减，但消息没有投递成功，就会出现库存被占用却没有订单的悬挂状态。

可以选择：

- 等待 Broker 确认后再返回；
- 使用事务消息；
- 将待投递事件与本地业务状态写入同一数据库事务，再由 Outbox 发布；
- 对失败投递记录补偿任务。

具体方案取决于入口状态存在哪里。关键是不能把“调用发送方法”当成投递成功。

## 消费者要默认消息会重复

网络超时可能导致 Broker 已收到确认，但消费者没有看到；进程也可能在处理完成后、提交消费位置前崩溃。很多系统因此采用至少一次语义，重复消息是正常情况。

消费者可以用订单 ID 做幂等键：

- 订单主键或业务键唯一；
- 用户和活动组合唯一；
- 条件插入或幂等记录；
- 重复消息返回已完成，而不是再次扣库存。

先查询再插入仍有并发窗口，最终需要数据库唯一约束。

## 数据库事务应该包住什么

消费者中的“扣数据库库存”和“创建订单”必须形成同一业务原子单元：

```text
begin
  conditional stock decrement
  insert order
commit
```

如果扣库存成功后订单插入失败，应回滚库存。事务方法还要通过正确的代理入口调用，避免声明式事务因为自调用而没有生效。

不要把耗时网络调用放进长数据库事务中，否则会延长锁持有时间。

## 消费失败如何处理

失败可以分为：

- 瞬时失败：数据库连接波动、短暂限流；
- 数据问题：字段非法、活动不存在；
- 代码问题：空指针、版本不兼容；
- 状态冲突：库存不足、唯一约束冲突。

只有瞬时失败适合自动重试。重试需要指数退避和最大次数，不能让一条永久失败消息阻塞整个分区。

超过重试次数的消息应进入可观察的失败队列或人工处理流程，并保留原始业务键与失败原因。

## Redis 与数据库如何对账

入口库存和持久化库存可能因为投递失败、消费失败或人工操作产生差异。活动结束后应按订单事实进行对账：

- Redis 成功资格数；
- 已持久化有效订单数；
- 失败或取消订单数；
- 剩余库存；
- 未完成的消息和补偿记录。

对账不仅用于活动结束，也可以作为运行时告警：差值持续扩大通常意味着异步链路发生故障。

## 订单状态帮助表达最终一致

创建订单前后可以使用明确状态：

```text
ACCEPTED → CREATED → PAID
        ↘ FAILED / EXPIRED
```

客户端查询到 `ACCEPTED` 时知道请求正在处理，而不是把“暂时不存在”当成失败。状态变化同样要有幂等和合法转移约束。

## 可观测性

至少监控：

- 生产成功率和确认延迟；
- 队列积压；
- 消费成功、重试和失败数量；
- 单条消息处理耗时；
- 数据库条件更新失败；
- 唯一约束冲突；
- Redis 与数据库的库存差异。

入口响应很快但消息积压持续增长，并不意味着系统健康。

## 总结

异步下单用削峰换来了状态复杂度。可靠实现依赖生产确认、消费者幂等、数据库事务、有限重试、失败收敛和最终对账。消息队列不是消除一致性问题，而是让我们用明确的状态和补偿机制管理它。
