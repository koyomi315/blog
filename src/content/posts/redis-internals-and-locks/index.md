Redis 对外提供 String、Hash、List、Set、Sorted Set 等数据类型，内部会根据数据规模和配置选择不同编码。理解这些结构，有助于解释内存占用和复杂度，但业务不应绑定某个版本的内部编码名称。

## Dict：哈希表基础

字典用于 Key 空间，也支撑多种数据类型。哈希表提供接近常数时间的查找，但要处理冲突和扩容。

Redis 为避免一次性扩容阻塞过久，会在后续操作中逐步迁移桶。渐进式 rehash 期间，查询需要考虑新旧表。

这提醒我们：单次命令复杂度看似稳定，并不意味着大 Key 或扩容没有延迟影响。

## 紧凑连续结构

字段少、内容短时，连续内存结构可以减少指针和对象头开销，缓存局部性也更好。数据增大后，Redis 可能切换到更适合更新和查找的结构。

旧版本常见 ZipList，后续版本大量使用 Listpack 等更安全的紧凑布局。讨论线上内存时应以实际 Redis 版本和对象编码为准。

## QuickList

List 既需要高效访问两端，又要控制每个元素单独分配的指针开销。QuickList 可以理解为链表节点中保存一段紧凑列表，在随机访问、两端操作和空间之间折中。

超大 List 仍可能产生阻塞式遍历或删除，不能因为底层结构优化就忽略集合规模。

## SkipList 与有序集合

跳表通过多层前进指针加速有序查找。Sorted Set 需要按 score 排序、范围查询和排名操作，跳表很适合这类需求。

它用额外指针换取平均对数级查找。与平衡树相比，跳表实现相对直接，也便于范围遍历。

## 大 Key 与热 Key

两类问题不要混淆：

- 大 Key：单个 Value 元素多或字节大，影响网络、内存和删除延迟；
- 热 Key：访问频率极高，造成单节点 CPU、带宽或连接压力。

治理方式不同。大 Key 需要拆分、渐进删除和限制；热 Key 需要本地缓存、读副本、分片或业务层削峰。

## 最小分布式锁

一个基本加锁操作需要原子地完成“不存在才写入”和“设置过期时间”：

```text
SET lock:key unique-owner NX PX lease-time
```

释放时必须检查持有者标识后再删除，并把检查与删除放在同一原子操作中。否则客户端 A 的锁过期后，客户端 B 获得新锁，A 可能误删 B 的锁。

## 租约与续期

固定过期时间存在两难：

- 太短：业务未完成锁已经过期；
- 太长：持有者崩溃后恢复慢。

可以使用自动续期，但续期也需要检测持有者是否仍存活，并在进程停顿、网络分区时接受租约可能失效的事实。

分布式锁保护的资源如果不能容忍两个持有者短暂同时执行，还需要 fencing token：每次获得锁得到单调递增编号，下游只接受更大的编号。

## 锁不是最终约束

以“一人一单”为例，即使使用 Redis 锁，数据库仍应有唯一约束。锁减少冲突，唯一约束守住最终不变量。

涉及库存时也应使用数据库条件更新。不要把所有正确性建立在单个 Redis Key 永远可靠之上。

## Redisson 等客户端的价值

成熟客户端通常封装了唯一持有者、原子释放、可重入和续期等能力。但使用库并不等于自动获得业务正确性，仍需决定：

- 锁粒度；
- 最大等待；
- 业务超时；
- Redis 故障策略；
- 下游最终约束。

## 总结

Redis 的性能来自数据结构和内存布局的组合，但大 Key、热 Key 和长命令仍会破坏低延迟。分布式锁则是一种租约协议，不是万能互斥。只有与数据库约束、幂等和故障策略结合，才能维护业务正确性。
