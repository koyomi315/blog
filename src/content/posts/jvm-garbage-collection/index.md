垃圾回收器解决两个问题：哪些对象已经不再可用，以及如何回收它们占用的空间。不同收集器的差异，主要体现在暂停、吞吐、内存占用和并发开销之间的选择。

## 可达性分析

Java 通常从一组 GC Roots 出发遍历引用关系。能够从 Roots 到达的对象被视为存活，其余对象才有机会被回收。

常见 Roots 包括：

- 线程栈中的引用；
- 已加载类的静态字段引用；
- JNI 等本地代码持有的引用；
- JVM 内部运行所需对象。

可达并不等于业务仍然需要。静态集合一直引用对象时，GC 会认为它们存活，这正是常见内存泄漏形式。

## 引用强度

Java 提供强、软、弱、虚等不同引用类型。弱引用常用于不阻止对象回收的关联结构；虚引用主要用于获知对象进入特定回收阶段并配合资源管理。

软引用受到内存压力和实现策略影响，不应被当成具有确定容量与淘汰语义的业务缓存。

## 三种基础回收算法

### 标记—清除

标记存活对象后清理未标记空间。实现直接，但会产生碎片，后续大对象可能找不到连续空间。

### 标记—整理

标记后把存活对象向一端移动，整理出连续空闲空间。减少碎片，但移动对象会增加成本。

### 复制

把存活对象复制到另一块区域，再整体释放原区域。适合存活率较低的区域，但需要保留复制空间。

现代收集器通常组合这些思想，并按区域或分代组织回收。

## 分代假设

大量对象生命周期很短，少数对象存活很久。分代收集据此把新对象和长期存活对象区别处理，以减少每次扫描范围。

但这不是 Java 规范强制的固定物理布局。区域化收集器也会动态选择回收集合。理解当前收集器的日志术语，比死记某一张年轻代/老年代示意图更重要。

## 吞吐量、暂停与内存

没有收集器同时在所有指标上最优：

- 吞吐量优先：希望应用执行时间占比更高；
- 延迟优先：希望单次暂停尽量短；
- 内存优先：希望元数据和并发标记结构占用更少；
- 可预测性优先：希望暂停分布稳定。

并发回收可以缩短部分停顿，但会与应用线程竞争 CPU 和内存带宽。低暂停不是没有成本。

## 常见收集器如何理解

不必先背完整参数表，可以按目标区分：

- 串行收集器：实现简单，适合资源受限或小堆；
- 并行收集器：强调吞吐量；
- G1：把堆划分为区域，按收益选择回收集合，兼顾大堆和可控暂停；
- 低延迟收集器：通过更强的并发和屏障设计缩短暂停，付出额外资源成本。

选择前应确认 JDK 版本、默认收集器、堆规模和服务目标，不要仅根据名称判断。

## Minor、Mixed 与 Full GC

不同收集器对事件命名略有差异。通常可以理解为：

- 只处理新对象区域的回收；
- 同时处理部分长期存活区域的混合回收；
- 需要更大范围停顿和整理的完全回收。

“出现 Full GC”是现象。根因可能是分配过快、晋升压力、碎片、元空间、显式 GC、配置不当或真正的泄漏。

## 排查 GC 问题

推荐按证据推进：

1. 观察堆使用曲线与 GC 后最低点；
2. 查看分配速率、晋升速率和暂停分布；
3. 判断是容量不足、瞬时流量还是持续增长；
4. 检查大对象、线程本地缓存和直接内存；
5. 必要时获取堆转储并分析支配树和引用链；
6. 先修复对象生命周期，再考虑参数调优。

如果每次 GC 后存活对象基线持续上升，更像泄漏或业务状态无限增长；如果基线稳定但回收频繁，可能是分配速率过高或堆配置偏小。

## 不要只看平均暂停

线上体验往往由尾延迟决定。应同时关注：

- 暂停 P95/P99；
- 最长暂停；
- GC 频率；
- GC CPU 占比；
- 分配失败；
- 服务请求延迟与 GC 时间的相关性。

## 总结

GC 调优的起点不是参数，而是对象生命周期和服务目标。先通过日志和内存分析确认问题属于分配、存活、碎片还是外部内存，再决定调整堆、收集器或代码。没有证据的参数堆叠，很容易用一种资源问题换来另一种。
