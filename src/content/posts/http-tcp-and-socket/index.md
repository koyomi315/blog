HTTP、TCP 和 Socket 经常一起出现，但它们不在同一抽象层：HTTP 定义应用如何交换消息，TCP/UDP 提供传输语义，Socket 则是操作系统暴露给应用的编程接口。

## HTTP 版本解决了什么

### HTTP/1.1

默认支持持久连接，多个请求可以复用 TCP 连接，减少重复握手。但同一连接上的请求和响应处理仍受到顺序与应用实现限制，浏览器通常使用多个连接提高并发。

### HTTP/2

HTTP/2 使用二进制帧和流，把多个请求复用在同一连接上，并提供头部压缩。它解决了 HTTP 层的请求串行问题，但所有流仍共享一个 TCP 连接，底层丢包会影响连接上的后续数据交付。

### HTTP/3

HTTP/3 建立在 QUIC 之上。QUIC 使用 UDP 承载，在用户态实现可靠传输、加密握手和独立流，减少一个流丢包对其他流的阻塞。

HTTP/3 不是“不可靠 HTTP”，可靠性由 QUIC 提供，而不是 TCP。

## TCP 如何提供可靠字节流

TCP 面向连接，向应用提供有序、可靠的字节流。主要机制包括：

- 序列号与确认；
- 校验和；
- 超时与快速重传；
- 接收窗口和流量控制；
- 拥塞控制；
- 乱序缓存与按序交付。

“可靠”并不意味着应用写入后对方业务一定处理成功。TCP 只能确认数据到达对端协议栈，应用仍需要自己的请求 ID、超时和业务确认。

## 三次握手

连接建立需要双方同步初始序列号，并确认双向通信能力：

```text
client → SYN
server → SYN + ACK
client → ACK
```

第三次确认让服务端知道客户端已经收到服务端的序列信息。握手也为连接选项协商提供载体。

## 四次挥手

TCP 是全双工连接，两个方向可以独立关闭。收到一方的 FIN 只表示该方向不再发送数据，另一方仍可能有数据未发送，因此确认与自己的 FIN 往往分开出现。

实际报文也可能合并，不能把“四次”理解成任何关闭场景都严格出现四个独立包。

## UDP 的边界

UDP 提供无连接的数据报服务：

- 保留报文边界；
- 不保证到达、顺序或唯一；
- 协议头和状态较少；
- 应用可以按需要实现重传、拥塞控制或容错。

实时音视频、DNS 和自定义可靠协议可能使用 UDP，但选择依据是应用语义，而不是“UDP 永远更快”。

## Socket 是什么

Socket 是操作系统提供的通信端点抽象。应用通过它使用 TCP、UDP 或其他协议。

TCP 服务端常见流程：

```text
socket → bind → listen → accept → read/write → close
```

客户端通常执行：

```text
socket → connect → read/write → close
```

监听 Socket 接收连接，`accept` 返回的新 Socket 才对应一条具体 TCP 连接。

## TCP 没有消息边界

一次 `write` 不一定对应对端一次 `read`。应用层必须定义帧，例如：

- 固定长度；
- 分隔符；
- 长度前缀；
- 自描述协议格式。

所谓“粘包”不是 TCP 把包错误粘在一起，而是应用错误地假设字节流保留写入边界。

## 常见状态码边界

- `401`：缺少有效认证信息；
- `403`：身份可能已知，但不允许访问资源；
- `502`：代理或网关从上游收到无效响应；
- `503`：服务当前不可用，可能过载或维护；
- `504`：代理或网关等待上游超时。

状态码描述协议语义，具体故障原因仍需要日志和追踪确认。例如 502 不只意味着“服务没启动”。

## 总结

HTTP 决定应用消息，TCP/UDP 决定传输语义，Socket 提供编程接口。把分层关系分清，才能正确理解连接复用、可靠性、消息边界和错误处理应该由哪一层负责。
