## 二、评测平台与实习工作

5. 详细介绍评测平台的业务场景、用途和闭环。
   - 当时回答：评测商家入驻相关的业务 Agent，观察其能否完成资料提交、资质检查等流程。归集有问题的 Case 后，由人工判断是 Agent、测试集覆盖还是评分标准存在问题，再为后续迭代提供依据。
6. 自动定时评测解决什么痛点，具体流程是什么？
   - 当时回答：将原来需要手动执行的能力串成周期性的线上巡检。主要分为按窗口收集历史 Trace 并构建测试集、执行评测、归集低分 Trace 三个阶段。
7. 追问：如何保证长链路异步任务可靠执行，各项措施分别用在哪里？
   - 当时回答：业务幂等键防止同一执行点重复创建；配置修改、Worker 领取任务时使用 CAS；阶段超时后重新投递，达到重试上限或执行失败时收敛到终态，避免长期停留在中间状态。
8. Tool Mock 服务做什么，为什么评测需要它？
   - 当时回答：Agent 重放时，工具调用结果可能随时间变化，影响评测比较。Mock 固定工具返回结果，帮助提高评测的可复现性。
9. Trace 是什么？
   - 当时回答：提到 Trace 是 JSON 形式的数据，记录中没有保留更完整的定义说明。

## 三、CAS、异步流程与个人职责

10. 具体说明 CAS 在哪些并发场景中使用，如何实现？
    - 当时回答：人工修改任务配置与扫描器更新计划执行时间可能并发，通过 revision 版本号控制修改。任务重投后，多个 Worker 可能竞争同一任务，通过预期任务状态控制申领及状态变更。
11. 追问：这里“异步”具体指什么，三个阶段如何串起来，为什么会有并发问题？
    - 当时回答：到时触发并创建执行后，后续任务在后台完成，平台可查询当前进度。三个阶段复用已有能力，再组织为串行流程；重试、自动扫描和人工修改会引入并发，需要相应防护。
12. 自动定时评测是你独立开发的吗，平台当时发展到什么阶段？
    - 当时回答：自动定时评测需求由自己开发，但复用了已有平台能力；平台当时还在初期，使用者不多，后续有不少功能需要完善。
13. 实习团队的定位、规模和人员构成如何？
    - 当时回答：自己理解为中台团队，原先与稳定性相关部门在一起，后来拆出小组，建设 Agent 评测、知识库等能力。小组仍在扩充，自己是组内唯一的实习生。

## 四、OnCall Agent 与 RAG 实践

14. 为什么做 OnCall Agent，希望实践哪些技术？
    - 当时回答：主要是实践 RAG、工具调用和 Agent 框架，理解知识库离线构建、在线检索，以及 ReAct、Plan-Execute；实现对话交互和辅助排障功能。
15. 追问：项目的业务背景、代码和学习资料从哪里来？
    - 当时回答：结合网上资料及与 AI 的讨论选择运维场景，学习开源教程和案例，再在案例基础上完成项目。
16. 知识库文档从哪里来，构建过程和在线检索如何进行？
    - 当时回答：通过 AI 编写文档，自己组织成 Markdown 语料。离线按标题、段落等语义结构分块，用 Embedding 模型生成向量，将文本块、向量及元数据存入数据库。
    - 在线检索时，提到先对 Query 做可能的改写，再用同一 Embedding 模型生成向量，召回相近的 Top K 内容，补入上下文供模型回答。
17. 追问：检索效果如何进一步改进，如何理解混合检索和精排？
    - 当时回答：自己只做了语义检索；后来了解可以结合向量检索和 BM25，错误码等信息更适合关键词匹配。
    - 对精排，当时理解为进一步比较 Query 与召回内容的相近程度，或者使用大模型判断，没有说明更具体的实现。
18. Agent Loop 和工具调用是自己实现还是框架封装，自己配置了什么？
    - 当时回答：主要使用 Spring AI 的 ReAct 封装，配置上下文、工具和模型参数，Loop 由框架提供。
19. 如何设计接近真实的运维场景，日志、监控等工具如何模拟？
    - 当时回答：知识库模拟运维文档、错误码说明和排障经验；设计查时间、查日志、查监控三个工具，预设 CPU、内存占用异常等返回结果，用 Mock 环境跑通辅助排障流程。

## 五、Coding Agent 与开发流程

20. 是否用后端或 Agent 技术解决过其他实际问题？
    - 当时回答：主要用于学习、面经整理、科研辅助，以及 GUI 等代码编写，多数借助 Coding Agent，没有特别复杂的其他项目。
21. 追问：实习中主要使用哪些 Coding Agent？
    - 当时回答：主要使用 Codex 和 Claude Code。
22. 追问：拿到需求后如何与 Coding Agent 配合，如何检查结果、沉淀知识？
    - 当时回答：先与产品对接、理解需求，再使用小组已有的开发工作流，结合 SDD 与 TDD，依次做需求澄清、技术设计、编码、检查、测试和归档。过程中允许返回前一阶段修改，并将相关知识沉淀到项目知识库，供后续开发使用。

## 八、整理建议
