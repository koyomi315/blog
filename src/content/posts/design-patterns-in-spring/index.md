设计模式不是需要背诵的类图，而是对重复设计问题的命名。Spring 代码里经常能看到这些模式，理解它们的边界比记住定义更有用。

## 策略模式：把变化隔离成实现

假设订单支持多种优惠方式，可以定义统一接口：

```java
public interface DiscountStrategy {
    String type();
    Money apply(Money origin);
}
```

每种优惠实现一个策略，业务服务按 `type` 选择。新增优惠时不需要继续扩展一串 `if-else`。

在 Spring 中，可以注入 `List<DiscountStrategy>`，启动时构造成映射。策略模式适合算法步骤相同、局部规则变化的场景；如果各实现连输入输出都不同，强行统一接口只会隐藏差异。

## 模板方法：固定骨架，开放步骤

批处理任务可能都有读取、校验、执行和记录结果几个阶段。抽象基类可以固定主流程，让子类覆盖特定步骤。

模板方法通过继承复用结构，适合骨架非常稳定的场景。业务组合经常变化时，优先考虑把步骤拆成协作对象，避免深继承层级。

## 工厂：封装创建决策

工厂负责根据配置或输入创建合适对象。Spring 的 IoC 容器本身就在管理对象定义、实例化和依赖装配，`FactoryBean` 则允许自定义复杂对象的创建过程。

不要为每一个简单构造器额外创建工厂。只有当创建过程包含选择、缓存、第三方初始化或生命周期逻辑时，工厂才真正减少复杂度。

## 代理：在调用边界增加能力

声明式事务、缓存和部分权限控制都可以通过代理在方法调用前后加入逻辑：

```text
调用者 → 代理 → 目标对象
```

代理擅长处理横切关注点，但也带来调用边界：对象内部的 `this` 调用不会再次经过外部代理。理解这一点可以解释很多“注解写了却不生效”的问题。

## 适配器：让接口不兼容的对象协作

接入不同短信或存储供应商时，第三方接口各不相同。应用可以定义自己的端口：

```java
public interface MessageSender {
    SendResult send(Message message);
}
```

每个供应商适配器负责参数转换、错误归一和返回值映射。业务层只依赖内部接口，供应商 SDK 的变化被限制在边界层。

## 观察者：一个事件，多种后续动作

订单完成后可能需要积分、通知和审计。发布领域事件可以让多个监听者各自处理，而订单核心流程不直接依赖所有下游。

同进程事件适合解耦模块，但不天然具备持久化和跨进程可靠性。关键业务不能因为使用了事件 API，就误以为获得了消息队列的交付保证。

## 装饰器与责任链

装饰器在保持相同接口的前提下逐层增加行为，例如为客户端增加重试、指标和缓存。责任链让请求依次经过多个处理器，例如认证、限流和参数校验。

两者结构相似，意图不同：装饰器强调能力叠加，责任链强调由链条中的节点决定处理或传递。

## 选择模式前先描述问题

可以先问三个问题：

1. 哪部分稳定，哪部分经常变化？
2. 变化发生在对象创建、算法选择还是调用过程？
3. 新增一种行为时，希望修改哪些文件？

如果无法说清正在解决的变化，添加模式往往只是增加间接层。

## 总结

好的设计模式让变化更局部：策略隔离算法，工厂隔离创建，适配器隔离外部接口，代理隔离横切能力，观察者隔离后续响应。模式是沟通设计的词汇，不是代码复杂度的目标。
