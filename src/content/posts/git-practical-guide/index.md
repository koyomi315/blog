Git 最重要的不是命令数量，而是理解状态如何流动。先建立工作区、暂存区和提交历史的心智模型，很多操作就不再依赖死记。

## 三个主要状态

```text
工作区 --git add--> 暂存区 --git commit--> 本地历史
```

- 工作区是正在编辑的文件；
- 暂存区是下一次提交准备包含的快照；
- 提交是带父节点的不可变快照。

`git status` 是最值得频繁使用的命令，它会告诉你文件处在哪个阶段。

## 一次提交只表达一件事

理想提交应当：

- 能独立说明一个变更意图；
- 不混入格式化、临时调试和无关文件；
- 提交信息解释“为什么改”；
- 在提交前通过相关检查。

可以用 `git diff` 查看未暂存变化，用 `git diff --staged` 检查即将提交的内容。暂存不是机械步骤，而是组织提交边界的机会。

## 分支是指向提交的可移动引用

创建功能分支并不会复制整个项目，它只是建立一个新的引用。日常协作可以保持：

```text
main ── stable history
  └── feature branch ── focused commits
```

短生命周期分支更容易审查和合并。一个分支同时包含多个主题，会让回滚与代码审查都变困难。

## merge 与 rebase 的取舍

`merge` 保留两个开发分支的关系，可能产生合并提交；`rebase` 把一组提交重新放到新的基点上，使线性历史更清晰，但会改写提交身份。

实用原则是：

- 尚未共享的个人分支可以整理历史；
- 已被其他人基于其开发的公共提交不要随意改写；
- 团队约定比个人审美更重要。

## 冲突是在合并意图

遇到冲突时，先理解两边分别想实现什么，再编辑最终内容。处理步骤通常是：

1. 查看冲突文件；
2. 手动形成正确结果；
3. 运行测试或构建；
4. 暂存解决后的文件；
5. 继续合并或变基。

只删除冲突标记并不代表冲突已经正确解决。

## 回退前区分三种需求

- 取消工作区修改：目标是本地尚未提交的内容；
- 修改最近提交：目标是提交内容或说明；
- 撤销已共享提交：目标是在历史中增加反向变更。

对已经推送并被协作使用的提交，优先使用生成新提交的撤销方式。重写公共历史会迫使其他人协调自己的分支。

执行任何丢弃操作前，先用 `git status` 和 `git diff` 确认目标。未提交内容通常最难恢复。

## 远程协作的基本节奏

```text
同步远程 → 完成本地小提交 → 再次同步 → 解决冲突 → 推送 → 代码审查
```

不要在示例、提交记录或公开文章中保留带凭据的远程地址。访问令牌应交给凭据管理器或安全的环境配置处理。

## `.gitignore` 不是保密机制

`.gitignore` 只影响未被跟踪的文件。密钥一旦进入提交历史，后来加入忽略规则并不能让它消失。此时应先撤销或轮换凭据，再按仓库治理流程处理历史。

## 总结

稳定的 Git 工作流来自小而清晰的提交、短分支、合并前检查和谨慎回退。遇到不确定操作时，先观察状态，再决定如何改变状态。
