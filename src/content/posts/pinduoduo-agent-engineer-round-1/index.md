## 一、自我介绍

## 二、评测平台与异步任务可靠性

2. 评测平台主要评测什么对象？业务 Agent 具体做什么？
   - 当时回答：评测外卖商家入驻相关的业务 Agent，判断它能否帮助商家提交资料、完成入驻流程。
3. 核心评价指标是什么？
   - 当时回答：平台提供一些预设评分维度，也支持根据业务需要配置评分器，举了回答是否简洁的例子。
4. 追问：平台如何提供评测基线？难道让不熟悉评测的业务开发自行配置评分器？
   - 当时回答：标准仍在建设。由专家标注线上历史 Trace，构建黄金测试集，再校准大模型评分器，使其评分接近专家标准；需要人工把关，不能无条件相信模型给出的分数。
5. 如何保障长链路异步任务的可靠性？幂等、CAS、状态收敛和重试分别用在哪里？
   - 当时回答：自动定时评测分为收集 Trace 并构建测试集、执行评测、归集低分 Bad Case 三个阶段。扫描到期任务时，通过任务 ID 与计划执行时间的联合唯一索引避免重复创建执行；阶段任务通过消息队列分发，CAS 用于控制多个 Worker 竞争领取任务，失败后可以重新分发。
   - 状态收敛的具体处理没有在这段回答中展开。
6. 追问：你的描述是否意味着消息队列存在重复消费？
   - 当时回答：先说“理论上是没有的”，随后解释，考虑的是 Worker 工作到一半失败后，重新发送同样的任务消息，让其他 Worker 领取并继续执行。
7. 使用的是 DDMQ 吗？了解它的底层实现吗？
   - 当时回答：使用的是 DDMQ，但没有看过底层代码，不清楚具体实现。
8. 追问：任务失败后为什么要用 CAS？为什么不直接使用消息队列的重试机制？
   - 当时回答：重试是向消息队列重新分发任务，再由 Worker 申领；没有进一步解释清楚消息队列重试与任务领取控制之间的关系。
9. 进一步追问：消息处理完成后如何确认消费？Worker 是否还要去数据库查询、领取任务？
   - 当时回答：称没有消费者返回的响应，只有分发过程；消息只包含任务 ID，Worker 根据 ID 到数据库领取任务，其他任务信息存放在数据库里。

## 六、Agent Harness、工具与上下文管理

15. Agent 的核心三部分是什么？进一步限定到 Harness 实现，核心组成是什么？
    - 当时回答：先从大模型决策中心说起，随后在工程实现的范围内提到工具调用和上下文组织；经提示后补充 Agent Loop。
    - 面试官补充：Agent Loop、上下文管理、工具定义等配置。
16. MCP v1 和 v2 有什么区别？迭代解决了什么问题？
    - 当时回答：不了解具体的版本迭代。
17. 工具定义有哪些核心字段？除名称外，哪些字段重要？
    - 当时回答：名称或 ID、描述、入参结构、返回结果结构，提到了 JSON Schema；描述用于帮助模型判断工具的用途和选择工具。
18. 工具调用结果是否进入上下文？后续模型请求能否看到这些结果？
    - 当时回答：会放入 messages，必要时先做精简；后续发送给模型时，模型可以看到相应结果。
19. 追问：单次工具返回很长，或持续追加导致上下文超长，怎么办？
    - 当时回答：简单结果可以直接放入；如果返回大量日志，提取后续决策需要的信息，而不是放入全部原始日志。
20. 进一步追问：上述结果精简如何落地？有没有可操作的办法？
    - 当时回答：承认之前的说法偏理想化，提出对返回量大的工具做特定适配，在工具侧人为干预输出。
21. 工具不断增多时，如何减少上下文占用及对模型判断的影响？
    - 当时回答：将工具分类成集合，采用渐进式披露，先暴露工具集，再按需寻找具体工具，减少工具描述带来的上下文占用和噪声。
22. 了解哪些上下文管理和 Compact 策略？如何实现？
    - 当时回答：保留最近几轮的完整内容，压缩更早的上下文，并识别、保留关键信息。还提到自己了解过 DeepSeek Harness，将交互记录持续追加成日志，再从日志构建供模型使用的上下文视图。
    - 追问：是否了解过 DeepSeek Harness？当时回答看过一些相关资料。

## 八、整理建议

以下是根据本场记录补充的事后建议：

- 复盘异步任务时，把消息消费、任务领取、执行失败与重试分开解释，准备一个 Worker 中途失败的具体例子，说明各层如何协作。
- 补练推理请求调度编程题，将排队、批次执行、取消和统计的要求落实到接口与测试。
- 对 Harness 和上下文管理，选一个实现沿调用链阅读，练习解释日志如何构建视图，以及工具结果精简如何落地。
