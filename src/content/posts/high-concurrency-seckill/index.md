秒杀系统的核心矛盾是：短时间内大量请求竞争极少库存，而真正的数据库写入能力有限。优化过程不能只看某个中间件，而要分析每一步把什么压力移到了哪里。

本文来自学习项目，数据仅用于理解设计演进，不代表生产系统容量。

## 阶段一：数据库同步下单

最直接的流程是：

```text
查活动 → 校验时间 → 查库存 → 查订单 → 扣库存 → 创建订单
```

它有三个问题：

- 每个请求都访问数据库；
- “查询库存”和“扣减库存”之间存在并发窗口；
- “查询订单”和“创建订单”之间也存在一人多单窗口。

仅在 Java 代码中先判断库存大于零，并不能防止多个事务同时通过判断。

## 阶段二：条件更新防止库存为负

把判断放进一条原子 SQL：

```sql
update voucher_stock
set stock = stock - 1
where voucher_id = ?
  and stock > 0;
```

根据受影响行数判断是否成功，可以利用数据库并发控制避免库存扣成负数。

这只解决超卖，不能自动保证一人一单，也没有降低热点行的竞争压力。

## 阶段三：按用户互斥

同一个用户的并发请求需要串行化。单机环境可以按用户 ID 加锁，但锁对象必须稳定，锁的范围也应覆盖“查询订单到创建订单”的完整临界区。

单机锁在多实例部署后失效，因为不同 JVM 看不到彼此的锁。

## 阶段四：分布式锁

Redis 分布式锁可以让多个应用实例围绕同一用户互斥。一个安全实现至少要处理：

- 加锁和过期时间原子设置；
- 唯一持有者值；
- 只释放自己的锁；
- 业务未完成时的续期；
- Redis 故障时的策略。

成熟项目通常使用经过验证的客户端实现，而不是只用 `SETNX` 加一个固定过期时间。

分布式锁解决了跨实例互斥，但主链路仍需要同步访问数据库，吞吐瓶颈没有消失。

## 阶段五：Redis 前置资格校验

可以把活动库存和用户购买集合预热到 Redis，并用 Lua 脚本在 Redis 内完成：

1. 判断活动是否存在或有效；
2. 判断库存是否大于零；
3. 判断用户是否已经购买；
4. 扣减 Redis 库存；
5. 记录用户购买资格。

Lua 脚本在 Redis 中连续执行，可以避免多个命令之间被其他请求穿插。

通过资格校验后，请求不必等待数据库订单真正写入，而是生成订单标识并发送异步消息。

## 为什么不让所有请求进入消息队列

消息队列用于削峰，但如果把明显无资格的请求全部写入队列，消费者仍要处理大量无效消息。Redis 前置校验先过滤：

- 库存已经售罄；
- 用户已经购买；
- 活动无效。

只有获得资格的请求进入下单队列，队列长度更接近实际库存规模。

## Redis 库存不是最终事实

Redis 扣减成功代表“获得下单资格”，不代表数据库订单已经完成。异步消费者仍可能失败，因此系统需要处理：

- 消息投递失败；
- 消费失败和重试；
- Redis 已扣但数据库未落单；
- 重复消费；
- 活动结束后的对账。

最终库存和订单事实通常仍落在持久化数据库中。Redis 是高并发入口的快速状态，不应成为无法校正的唯一事实来源。

## 唯一约束是最后防线

即使入口已经判断一人一单，数据库仍应对“用户 + 活动”建立唯一约束。原因包括消息重复、代码缺陷、数据修复和其他写入入口。

应用层锁和 Redis 校验用于减少冲突，数据库约束负责守住最终不变量。

## 需要观测什么

一次完整压测应至少记录：

- 入口请求量和拒绝量；
- Lua 执行延迟；
- 获得资格的请求数；
- 消息积压和消费速率；
- 数据库写入延迟与冲突；
- 重复订单约束冲突；
- Redis 与数据库库存差异。

只看平均响应时间会掩盖队列积压和最终落单延迟。

## 总结

秒杀链路的演进不是“加了 Redis 就高并发”，而是逐步解决不同问题：条件更新防超卖，按用户互斥防重复资格，Lua 把校验前置并保证原子性，消息队列把持久化移出同步链路，数据库唯一约束守住最终事实。理解每一步的边界，才能处理它引入的新故障。
