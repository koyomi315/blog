## 一、自我介绍

1. 请做一下自我介绍，介绍实习和项目经历。
   - 当时回答：介绍了滴滴国际化业务部门的 Agent 评测平台实习，主要参与自动定时评测和 Tool Mock；个人项目包括面向运维场景的 OnCall Agent，以及使用 Redis 处理防超卖、一人一单和缓存问题的秒杀项目。

## 二、Go 与 AI 辅助开发

2. 此前主要使用 Java，实习时如何学习 Go 并完成开发？掌握到什么程度？
   - 当时回答：开发主要借助 AI。入职学习阶段花约一周，一边了解业务，一边学习 Go 基础语法，达到能读懂生成代码的程度；没有深入学习底层机制。
3. 使用 AI 辅助开发时，如何比较技术方案并作出选择？
   - 当时回答：先让 AI 列出几种方案；遇到不理解的技术，会另开对话了解，再结合业务需求选择，不直接照搬方案。
4. 产品需求如何交给你？如何将 PRD 和沟通所得的需求提供给 AI？
   - 当时回答：既有 PRD，也会通过会议补充和对齐需求。所用内部文档没有开放对应的工具访问权限，因此主要复制到本地，再向 AI 说明需求和设计目标。
5. 实习中用过哪些 Coding Agent 和模型？分别承担什么工作？
   - 当时回答：使用过 Claude Code、Codex，也用过 DeepSeek 配合其他编程工具。结合可用额度，需求分析和技术设计更多使用 Claude，开发更多使用 GPT，DeepSeek 用于部分问题排查和文档工作。具体模型版本记不清楚。
6. 如何比较这些模型的效果？有什么实际例子？
   - 当时回答：个人体感是 Claude 给需求和技术方案较好，GPT 编程较好。一次 GPT 排查问题效果不佳，换用 DeepSeek 后发现了此前没注意到的代码细节，因此也会交叉使用。这是当时的使用感受。
7. 了解不同大模型 API 的协议差异吗？
   - 当时回答：主要使用已封装的接口，配置 base URL 和 API key。理解为不同 JSON 字段规范，但没有具体研究协议之间的底层区别。

## 三、OnCall Agent 与编排

8. 向量数据库、Embedding 模型如何选型？运维文档如何切分？
   - 当时回答：向量数据库选择 Milvus，考虑它专注向量检索、使用较广；Embedding 选择千问 embedding-text-v4，考虑性能、中文语料，以及付费和网络访问的便利性。运维知识文档采用 Markdown，按分级标题、段落等语义结构切分。
9. 如何理解 ReAct 的 Agent loop？从用户 query 到工具调用和最终回答，流程是什么？
   - 当时回答：将 query、系统提示词和工具说明提供给模型；模型需要外部信息时发起工具调用，由框架执行工具，将结果送回模型继续判断，直到不再调用工具并生成回答。实际项目中的循环由框架提供。
10. Planner 和 Executor 如何分工、配置和协作？
    - 当时回答：Planner 的提示词强调规划职责，将 Executor 作为类似工具的执行者；Executor 配置执行者身份和可用工具。Planner 分解任务并交给 Executor 执行，接收结果后继续规划或推进后续步骤。
11. 如何保存规划任务的状态和进度，支持后续持续执行？
    - 当时回答：当前方案没有专门的持久化状态存储，更多依赖上下文。认为可以参考 spec 编程，将需求、拆分任务及进度持久化，每完成一步就标记完成，未完成时也保存当前状态。这是当时提出的改进思路。

## 四、Agent 评测平台与定时任务

12. 介绍评测平台的整体流程。线上评测与离线评测有什么区别？
    - 当时回答：业务 Agent 的历史 Trace 保存在 Langfuse，评测平台同步 Trace 并构建测试集。线上评测直接评价历史 Trace 的表现；离线评测将测试集输入重放给业务 Agent，再对新的输入输出评分。
13. 离线重放如何保证输入和外部依赖可复现？除了 Tool Mock，还控制了什么？
    - 当时回答：测试集输入固定；同一用例调用同一工具、传入相同参数时，Mock 返回相同结果。知识库检索当时尚未接入，其他依赖还没有做更多控制。
14. 如何判断大模型评测分数是否可信、是否符合人工判断？
    - 当时回答：平台主要依赖大模型评分，但直接得到高分或低分不一定具有实际参考价值。需要先由人工标注 Trace，形成黄金测试集，再让模型评分更符合人工判断。这部分当时仍需要推进。
15. 评测平台是否已经实际反馈到业务？产品需求如何推进？
    - 当时回答：当时尚未真正将评测结果反馈到业务方；产品仍在与负责人讨论新需求，确认后交给开发实现。
16. 自动定时评测如何实现？长链路任务中的重复创建、并发领取和异常状态如何处理？
    - 当时回答：外部定时平台每分钟调用接口，检查计划是否到期，再创建执行任务。流程包括收集 Trace、评分和归集低分 Badcase，通过消息队列分配异步任务，并用任务状态记录阶段。
    - 追问：重复触发如何避免创建多个任务？当时回答以“任务 ID＋计划触发时间”作为业务幂等键。
    - 追问：多个 Worker 如何避免同时领取同一任务？当时回答采用 CAS 思路，检查前置状态，条件满足才推进状态并写入 Worker ID，类似租约申领。
    - 追问：任务失败或长时间卡住怎么办？当时回答通过异步检查收敛状态，对长期未领取、执行中但状态不更新的任务进行处理；也会检查实际工作状态，已成功则推进后续阶段。
17. 定时接口处理比较慢，上一次调用还没处理完，下一次又触发了，会怎样？
    - 当时回答：测试时没有遇到这个问题；接口主要负责触发并创建任务，长耗时流程由后续异步任务承接。没有进一步完整说明两次接口调用实际重叠时的行为。
18. 如何判断计划到期？是否通过时间窗口触发？
    - 当时回答：按时间窗口判断，只触发当前这一分钟内到期的任务。

## 五、现场题：Agent loop 与扩展设计

19. 写一个 Agent loop，不限定语言，可以使用伪代码说明思路。
    - 题目重点：表达对 Agent loop 执行流程的理解。
    - 现场代码及具体完成情况未记录，以下为后续讨论中保留的思路。
20. Agent loop 在什么情况下结束或中断？需要返回哪些信息？
    - 当时回答：提到 token 使用限制、轮数限制、超时和正常结束；中断前最好保存上下文，并在返回结果中标注结束原因。讨论中也澄清过，所说 token 限制指向使用计费。
21. 上下文过长时如何处理？是否设计了检测与压缩？
    - 当时回答：当时尚未设计，需要检测上下文长度，并考虑压缩。
22. 单次 Agent loop 调用内，历史消息如何维护和传递？一次函数调用的边界是什么？
    - 当时回答：一次调用接收初始 query，在 loop 内持续追加历史消息。这部分讨论针对单次 loop 调用。
23. 如果加入 Skill，如何发现、加载和执行？如何处理用户显式触发？
    - 当时回答：在提示词中提供可用 Skill 的名称和简短介绍，由模型决定是否加载；如果 query 已显式触发某个 Skill，则应加载。纯提示词型 Skill 作为上下文加载，带可执行内容的 Skill 则类似工具调用，结合任务决定执行内容。
24. 如何理解并接入 Memory？全量加载与按任务检索加载如何处理？
    - 当时先询问 CLAUDE.md 是否也算一种 Memory，之后围绕跨对话积累、主动学习或用户要求记录的信息继续讨论。
    - 当时回答：可以每次作为系统提示词加载，也可以针对当前任务检索，再确定是否加载。
