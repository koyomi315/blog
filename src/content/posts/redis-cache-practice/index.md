本文来自一个本地生活类学习项目。缓存的目标并不是“尽可能把数据放进 Redis”，而是在可接受的一致性范围内降低数据库压力和接口延迟。

## 先区分三个问题

### 缓存穿透

请求的数据在缓存和数据库中都不存在。攻击者或错误客户端持续请求不存在的 ID，每次都绕过缓存访问数据库。

### 缓存击穿

某个高频访问的 Key 失效，大量请求同时发现缓存未命中，并发查询数据库和重建同一个缓存。

### 缓存雪崩

大量 Key 在相近时间失效，或缓存服务整体不可用，造成大量流量同时转向数据库。

三个问题的触发条件不同，解决方案也不能混用。

## 缓存穿透：缓存空值

对于“按 ID 查询店铺”这类数据量有限的场景，可以在数据库确认不存在后，把空结果写入 Redis：

```text
cache miss
  → query database
  → not found
  → cache empty marker with short TTL
```

后续相同请求可以在缓存层结束。空值必须设置较短 TTL，避免攻击者用大量随机 ID 占满内存。

这种方案实现简单，但存在一个竞态：数据写入数据库后，旧的空值还没有过期，客户端会短暂看到“不存在”。创建数据时主动删除对应空值可以缩短窗口。

数据规模更大或非法 Key 变化极多时，可以在入口增加布隆过滤器。但布隆过滤器存在误判，并且要考虑新增、删除和重建流程。

## 缓存击穿：互斥重建

当热点 Key 失效时，可以只允许一个线程访问数据库并重建缓存：

```text
cache miss
  → try lock
      → success: query database → rebuild cache → unlock
      → failure: wait briefly → retry cache
```

锁本身也需要：

- 唯一持有者标识，避免误删他人的锁；
- 过期时间，避免进程崩溃后永久占用；
- `finally` 释放；
- 对等待次数和总时长设置上限。

互斥重建倾向于保证新鲜数据，但锁竞争会增加尾延迟。

## 缓存击穿：逻辑过期

另一种方案是不让 Key 物理过期，而是在 Value 中保存业务过期时间：

```json
{
  "expireAt": "logical-time",
  "data": {}
}
```

请求命中后：

- 未逻辑过期：直接返回；
- 已逻辑过期：尝试获取重建锁；
- 获取成功：异步重建，当前请求仍返回旧值；
- 获取失败：直接返回旧值。

逻辑过期把“等待新数据”改为“先返回旧数据”，可用性更高，但只能用于允许短暂陈旧的场景。库存、权限和账户余额通常不适合这样处理。

## 数据更新：先更新数据库，再删除缓存

读多写少的普通业务常采用 Cache Aside：

```text
read:  cache → database → cache
write: database → delete cache
```

写入时选择删除而不是直接更新缓存，原因是：

- 缓存结构可能是多个数据源的组合；
- 连续写入时每次更新缓存会产生无效计算；
- 删除后由下一次真实读取重建更简单。

但“更新数据库后删除缓存”仍存在短暂不一致窗口，也可能因为删除失败留下旧值。因此还需要：

- 删除失败重试；
- 通过消息或变更日志异步补偿；
- 为缓存设置合理 TTL 作为最终兜底；
- 对强一致数据绕开缓存或采用更严格协议。

## 缓存雪崩的处理

针对大量 Key 同时过期，可以组合：

- TTL 加随机抖动；
- 热点数据提前刷新；
- 请求限流和降级；
- 多级缓存；
- 缓存集群和故障隔离；
- 数据库侧的容量保护。

仅给 TTL 加随机数不能解决 Redis 整体故障，因此仍需要降级和数据库保护。

## 如何验证方案

缓存方案不能只靠接口返回正确来验证。至少观察：

- 缓存命中率；
- 数据库查询次数；
- 重建锁竞争和等待时间；
- 空值数量；
- P95/P99 延迟；
- 删除缓存失败次数；
- 返回旧数据的最长时间。

压力测试也要区分正常热点、Key 刚失效、不存在 ID 攻击和缓存不可用等场景。

## 总结

缓存穿透解决的是“不存在的数据”，缓存击穿解决的是“单个热点失效”，缓存雪崩解决的是“大量缓存同时失效或服务不可用”。方案选择最终取决于业务能否接受旧数据、数据库承载能力和故障恢复要求，而不是某个固定模板。
