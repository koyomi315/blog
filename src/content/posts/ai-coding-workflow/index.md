AI Coding 的效果不只取决于模型，也取决于开发者如何提供上下文、拆解任务和验证结果。随意说一句“帮我改一下”有时能工作，但难以形成稳定流程。

## 先让 Agent 理解项目

代码只能表达实现，很多约定并不在代码里：为什么选择某个框架、哪些目录不能修改、测试命令是什么、兼容到哪个版本。这些信息适合写进仓库级指令文件。

一份简洁的项目记忆可以包含：

- 项目目标和技术栈；
- 启动、测试、构建命令；
- 目录职责和主要入口；
- 数据、安全和兼容性约束；
- 当前阶段的已知问题。

它应当是团队文档，而不是给某个模型准备的神秘提示词。内容越接近真实工程约定，换工具时迁移成本越低。

## 阅读代码要从问题出发

让 Agent 无差别解释整个仓库会产生大量低价值上下文。更有效的是围绕一个问题逐层展开。

### 先理解文件职责

```text
这个文件负责什么？
它在调用链中的上游和下游是什么？
哪些公开方法承担核心行为？
```

### 再理解具体流程

```text
请按执行顺序梳理这个方法。
标出数据状态变化、数据库操作、缓存访问和外部调用。
说明异常发生时会走到哪里。
```

### 最后追问设计原因

```text
为什么这里使用事务、锁或异步队列？
这个选择解决了什么问题？
它引入了哪些新风险？
```

问题从“是什么”进入“怎么运行”，最后到“为什么这样设计”，能够避免停留在逐行翻译代码。

## 改代码前先定义完成条件

一个可执行任务至少要说明：

- 当前行为；
- 期望行为；
- 不允许改变的行为；
- 涉及范围；
- 验证方式。

例如“给接口加缓存”缺少关键边界；更好的描述应说明缓存对象、键、失效策略、数据一致性要求，以及用什么测试确认没有返回过期权限数据。

## 复杂任务先计划再修改

当任务跨越多个模块时，可以要求 Agent 先输出：

1. 需要读取的文件；
2. 预计修改的组件；
3. 数据和调用链变化；
4. 风险与回滚方式；
5. 分阶段验证命令。

计划不是为了增加文档，而是让错误假设在写代码前暴露。对于单行修复则不必强行套用重流程。

## 用引用缩小上下文

明确指出文件、目录、函数或报错信息，可以减少 Agent 搜索和猜测。例如提供失败测试名称，比只说“测试挂了”更有效。

但不要只发送孤立代码片段。缺少调用方、类型定义和测试时，模型容易生成局部正确、全局不兼容的修改。

## 权限模式要与任务匹配

常见操作可以分成：

- 阅读、搜索和状态查询；
- 工作区内代码编辑；
- 依赖安装、长时间命令和网络访问；
- 删除、发布和外部系统写入。

日常代码修改可以提高自动化程度，但不可逆操作仍应明确确认。权限越高，对路径限制、审计和验证的要求也越高。

## 长任务需要可恢复状态

当工作无法在一次会话完成时，只依赖聊天记录并不可靠。可以维护一个简短进度文件：

```markdown
## 已完成
- 已定位登录失败来自令牌刷新逻辑
- 已补充刷新成功和失败测试

## 当前问题
- 并发刷新会产生重复请求

## 下一步
- 比较单飞请求与分布式锁方案
- 运行认证模块集成测试
```

这份记录既帮助 Agent 续接，也方便人类检查实际进度。

## 验证是工作流的一部分

完成代码编辑不等于完成任务。一个可靠的结束顺序通常是：

1. 检查修改差异；
2. 运行最小相关测试；
3. 运行类型检查或静态分析；
4. 对高风险改动运行更大范围测试；
5. 汇总改动、验证证据和剩余风险。

如果验证失败，Agent 应报告实际输出，而不是用“看起来没问题”结束任务。

## 建立自己的反馈模板

对于频繁执行的任务，可以沉淀模板：

- 修复缺陷：复现 → 定位 → 最小修改 → 回归测试；
- 新增接口：契约 → 参数校验 → 业务逻辑 → 测试 → 文档；
- 重构：行为基线 → 小步修改 → 持续测试 → 差异检查；
- 代码评审：正确性 → 安全性 → 边界 → 可维护性 → 验证缺口。

这些模板比堆积“万能 Prompt”更容易复用，因为它们描述的是工程反馈回路。

## 总结

高质量 AI Coding 工作流由四件事组成：让项目约定可读取，让问题边界足够清晰，让修改权限受到控制，让每一步都有可观察的验证。模型能力会持续变化，但这套工程方法仍然适用。
