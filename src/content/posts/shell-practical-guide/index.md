Shell 的价值在于把小工具组合成可重复的流程。它也很容易因为空格、通配符和错误处理造成意外，因此需要同时理解表达能力与风险边界。

## 命令、参数与退出状态

命令执行后会返回退出状态，`0` 通常表示成功，非零表示失败。`&&` 只在前一条成功时继续，`||` 则在前一条失败时执行后续命令。

脚本不应该仅依靠终端输出判断成功。自动化流程要检查退出状态，并把失败传播给调用者。

## 管道传递标准输出

管道把前一个进程的标准输出连接到后一个进程的标准输入：

```bash
printf '%s\n' "alpha" "beta" | sort
```

管道适合逐步过滤和转换文本。调试复杂管道时，可以拆开每一段检查中间结果，避免某一步把数据意外清空。

## 重定向区分输出与错误

程序通常有标准输入、标准输出和标准错误三个通道。把普通结果写入文件时，错误仍然可以留在终端或独立日志中。

覆盖写入和追加写入的含义不同。执行前先确认目标路径，尤其不要把变量为空时的路径交给覆盖或删除命令。

## 引用规则决定变量如何展开

包含空格或通配符的变量必须正确引用：

```bash
target_dir="./build output"
mkdir -p -- "$target_dir"
```

双引号允许变量展开并保持参数整体，单引号通常保留字面文本。未引用变量可能被拆成多个参数，或触发通配符匹配。

`--` 常用于告诉命令后面的内容是参数而不是选项，能够避免以连字符开头的文件名被误解。

## 脚本的安全默认值

常见 Bash 脚本会启用更严格的错误处理：

```bash
set -Eeuo pipefail
```

它可以让未定义变量、失败命令和管道中的失败更早暴露。但这不是万能开关：某些允许失败的检查需要显式写进条件分支，也要理解子 Shell 和命令替换的行为。

## 临时文件与清理

不要手工猜测临时文件名。应使用系统提供的安全临时目录或文件创建工具，并在退出时清理。

删除操作尤其要做到：

- 目标来自可信输入；
- 路径已经规范化并核对；
- 不允许空变量展开成宽泛路径；
- 尽量限制在明确工作目录；
- 重要数据优先采用可恢复方式。

## 文本处理工具各司其职

- `rg` 适合快速搜索文件和内容；
- `sed` 适合流式替换；
- `awk` 适合按字段处理记录；
- `sort`、`uniq`、`cut` 适合简单集合操作；
- `jq` 适合 JSON，不要用正则解析结构化 JSON。

当脚本开始包含复杂数据结构、并发或大量错误分支时，换成通用编程语言通常更可维护。

## 可重复比简短更重要

一条很长的命令可能适合临时探索，但进入团队脚本后需要变量名、输入校验、日志和使用说明。自动化脚本还应避免依赖个人机器上的固定路径、别名和交互式配置。

## 总结

Shell 擅长组合工具和自动化短流程。可靠脚本需要正确引用变量、检查退出状态、谨慎处理路径，并为失败留下可观察的信息。
