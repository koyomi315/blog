GNU Radio 的核心抽象是流图：Block 负责一种信号处理操作，连接负责传递连续样本或消息。入门时最重要的不是记住所有模块，而是让每一步都可解释、可观察。

## 先从纯软件闭环开始

在接入射频硬件前，可以先构造最小流图：

```text
Signal Source → Throttle → Frequency Sink / Time Sink
```

这样可以验证数据类型、采样率和频谱显示是否符合预期。纯软件流图没有硬件提供采样节奏时，需要用 Throttle 限制运行速度；接入 USRP 等硬件后，采样节奏由设备驱动，通常不再额外添加 Throttle。

## 采样率是整张流图的共同约束

每条流连接都在传递离散样本。Block 不一定知道“秒”，它通常只知道每次处理多少样本，因此采样率决定了时间轴与频率轴的真实含义。

设计流图时应明确：

- 源端输出采样率；
- 插值和抽取倍率；
- 滤波器过渡带；
- Sink 期望的采样率；
- 每段数据类型和 item size。

如果中间做了抽取却没有同步修改可视化 Sink 的采样率，频谱坐标会看起来合理，但实际标度是错的。

## 复数样本表示基带 I/Q

GNU Radio 中常见的 complex 流用复数样本表示 I/Q：

$$x[n] = I[n] + jQ[n]$$

它可以同时表达幅度和相位。Float、Complex、Byte 等端口不能随意连接，必要时应使用显式转换 Block，让数据含义保持清楚。

## 用流图测量相位差

两个复信号的相位差可以通过共轭相乘得到：

$$z[n] = x_2[n]x_1^*[n]$$

`arg(z[n])` 即瞬时相位差。一个可读的流图可以组织为：

```text
x1 → Conjugate ─┐
                 Multiply → Complex to Arg → Average → Number Sink
x2 ─────────────┘
```

移动平均只能降低随机波动，不能修复频偏、不同步或硬件本振造成的系统相位漂移。

## Variable 与参数化

把采样率、中心频率、增益和带宽定义为变量，可以避免多个 Block 各自保留一份常量。调整参数时，先确认哪些属性支持运行时更新；有些硬件或滤波器参数改变后需要重新初始化。

生成的 Python 代码适合帮助理解流图如何落到 API，但不应直接在自动生成文件里长期维护业务逻辑。可复用算法更适合封装为层次化 Block 或自定义模块。

## 接入 USRP 的最小检查顺序

1. 用 UHD 工具确认设备可发现；
2. 从较低采样率开始；
3. 设置明确的中心频率、增益和天线端口；
4. 用 Frequency Sink 确认目标信号位置；
5. 观察是否出现 overflow、underrun 或网络告警；
6. 再逐步提高采样率并加入算法模块。

一次改变多个参数会让故障定位变得困难。实验参数应集中记录，但公开记录不要包含设备序列号、真实网络地址或个人目录。

## 常见故障的分类

- 没有数据：设备发现、端口、中心频率或权限问题；
- 数据断续：主机吞吐、USB/网络链路或调度不足；
- 频谱位置错误：采样率、抽取倍率或频率偏移配置错误；
- 波形削顶：增益过高导致前端或 ADC 饱和；
- 相位不稳定：频率参考、时间同步、本振或信噪比问题。

先给问题分类，再修改配置，比围绕一条日志盲目调参更有效。

## 总结

GNU Radio 流图本质上是一个带速率和类型约束的数据处理图。先用纯软件验证算法，再接入硬件；让关键中间结果可视化；每次只改变一个变量，实验才能复现。
