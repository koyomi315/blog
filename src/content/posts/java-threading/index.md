并发问题经常表现为“偶尔出错”。要分析它，需要先理解线程的执行状态、线程之间共享什么，以及阻塞和唤醒由谁控制。

## 进程、线程与协程

- 进程拥有独立虚拟地址空间，是资源隔离的重要边界；
- 线程是操作系统调度执行的基本单位，同一进程内线程共享堆、文件描述符等资源；
- 协程或用户态任务通常由语言运行时调度，创建与切换成本较低，适合大量等待型任务。

Java 应用中的传统平台线程通常映射到操作系统线程。现代 Java 还提供虚拟线程等运行时调度方案，但共享数据的正确性问题不会因此自动消失。

## `start()` 与 `run()`

调用 `run()` 只是普通方法调用，代码仍在当前线程执行。调用 `start()` 才会请求 JVM 启动新线程，并由新线程执行 `run()`。

同一个 `Thread` 实例只能启动一次。需要重复提交任务时，应把任务与线程生命周期分开，交给执行器管理。

## Java 的六种线程状态

`Thread.State` 定义：

| 状态 | 含义 |
|---|---|
| `NEW` | 已创建但尚未启动 |
| `RUNNABLE` | 可运行，可能正在 CPU 上执行或等待调度 |
| `BLOCKED` | 等待进入 `synchronized` 临界区 |
| `WAITING` | 无限期等待其他线程动作 |
| `TIMED_WAITING` | 带超时的等待 |
| `TERMINATED` | 执行结束 |

Java 的 `RUNNABLE` 同时覆盖操作系统层面的就绪和运行状态，不能仅凭它判断线程正在占用 CPU。

## `sleep` 与 `wait`

`Thread.sleep`：

- 让当前线程暂停指定时间；
- 不要求持有对象监视器；
- 不会主动释放已经持有的锁。

`Object.wait`：

- 必须在持有对应监视器时调用；
- 调用后释放该监视器；
- 需要 `notify`、`notifyAll`、中断或超时才能继续竞争锁。

条件等待应放在循环中重新检查：

```java
synchronized (queue) {
    while (queue.isEmpty()) {
        queue.wait();
    }
    consume(queue.remove());
}
```

原因包括虚假唤醒，以及多个线程被唤醒后条件可能已被其他线程改变。

## `notify` 与 `notifyAll`

`notify` 唤醒等待同一监视器的一个线程，具体选择不受业务控制。`notifyAll` 唤醒所有等待线程，它们随后重新竞争锁并检查条件。

当多个条件共用一个监视器时，错误使用 `notify` 可能唤醒无法继续的线程。更复杂的协作通常适合使用 `Lock`/`Condition` 或更高层并发工具。

## 中断是协作协议

Java 没有通用且安全的“强制杀死线程”。`interrupt()` 设置中断状态，并使部分阻塞方法抛出 `InterruptedException`。

任务需要主动响应：

```java
while (!Thread.currentThread().isInterrupted()) {
    doOneUnit();
}
```

捕获 `InterruptedException` 后如果不能立即退出，应恢复中断标记：

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}
```

吞掉中断会让上层无法取消任务。

## 什么是线程安全

线程安全不是“加了锁就安全”，而是并发执行仍满足业务不变量。常见问题包括：

- 原子性：复合操作被其他线程穿插；
- 可见性：一个线程看不到另一个线程的最新写入；
- 有序性：允许的重排序破坏错误假设；
- 活性：死锁、活锁或长期饥饿。

解决策略包括不可变对象、线程封闭、原子类、锁、并发集合和消息传递。优先减少共享可变状态，通常比给所有地方加锁更容易验证。

## 线程转储是重要证据

线程卡住时，可以从线程转储中观察：

- 大量线程阻塞在哪个监视器；
- 是否存在死锁；
- 线程池是否耗尽；
- 哪些线程长期运行；
- 调用栈是否集中在外部 IO。

状态只是入口，最终要结合持锁关系和调用栈判断。

## 总结

线程模型的核心是共享状态与协作。理解状态、监视器、中断和内存可见性，才能判断代码是在正常等待，还是已经发生竞态、死锁或资源耗尽。
