## 三、Tool Mock 项目深挖

7. 评测时为什么需要对工具调用做 Mock？
   - 当时回答：一是避免评测流量调用真实工具，影响业务后台；二是固定工具返回结果，减少数据库状态等外部变化带来的无关变量，让评测更可比；三是直接查询预设响应，减少真实工具调用的开销，加快评测。
8. 追问：目前 Tool Mock 有多少个 Tool？
   - 当时回答：没有给出具体数量。我解释了需要 Mock 的数量取决于业务 Agent 有多少工具，以及哪些工具需要被模拟；返回稳定、不会明显影响业务的工具可以考虑真实调用。当时观察到平台使用还不算多。
9. 追问：Mock 的响应数据从哪里来，如何构建？
   - 当时回答：有两种方式。一种是手工构建 JSON 数据，上传后配置对应 Agent 和工具；另一种是从历史 Trace 中拉取真实工具调用记录，同步为 Mock 响应数据。
10. 追问：Tool Mock 如何接入业务 Agent？工具调用时怎样返回对应的 Mock 响应？
    - 当时回答：需要业务 Agent 配合接入 SDK。工具调用时区分真实业务流量与评测流量：真实业务调用真实工具，评测调用可以路由到 Tool Mock 平台。评测场景也可配置为真实调用；使用 Mock 时，结合配置和测试 Case 匹配数据库中的响应，再返回给 Agent。
11. 追问：Tool Mock 中，你认为有哪些难点或值得讲的点？
    - 当时回答：直接对比 JSON 字符串会受到空格、字段顺序等因素影响，需要处理这些差异；此外，入库和查询时计算对应哈希，帮助快速查找响应记录。当时主要展开了这两点。

## 四、自动定时评测与任务可靠性

12. 介绍一下自动定时评测的流程和难点，如何保证异步任务可靠性？
    - 当时回答：定期触发三个阶段：按时间窗口筛选 Trace 构建评测集、执行评测、按分数阈值收集低分 Trace，归集为 Bad Case 集。这三块原本已有基础能力，我主要将其复用并编排为自动流程，处理状态流转、重试和并发竞争。
    - 创建执行的幂等：外部定时调用接口，扫描到期的任务配置；用任务 ID 和计划执行时间组成唯一约束，避免同一计划时间重复创建执行记录。
    - Worker 并发申领：消息队列分发工作，重试可能使多个 Worker 收到同一任务；通过 CAS 思路按预期状态申领，再记录 Worker ID，建立租约。
    - 异常状态收敛：定期扫描异常状态，将下游已经失败、但执行记录仍停留在执行中的任务收敛为失败。

## 六、现场算法题

15. [LeetCode 33：搜索旋转排序数组](https://leetcode.cn/problems/search-in-rotated-sorted-array/)。
    - 题目要求：原本升序且元素互异的数组经过旋转，查找给定目标值；存在则返回下标，不存在返回 `-1`，要求时间复杂度为 `O(log n)`。
    - 当时思路：先找到数组最小值，确定两段有序区间的分界点；判断目标值应在哪一段，再对该段二分查找，同时兼容整个数组仍有序的情况。
    - 完成情况：现场表示代码已写完，并讲解了思路；具体代码、测试反馈和通过情况未记录。
