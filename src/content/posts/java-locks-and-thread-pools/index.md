并发工具解决的是不同层次的问题。`volatile` 不能替代复合操作的互斥，线程池也不能自动让任务更快。选择之前要先明确共享状态和资源瓶颈。

## `synchronized`

`synchronized` 提供互斥和内存可见性。进入同一监视器的临界区时，同一时刻只有一个线程执行；退出锁之前的写入，对随后获得同一锁的线程可见。

锁对象必须稳定且范围清晰。下面的代码如果 `account` 被替换，线程可能锁住不同对象：

```java
synchronized (account) {
    // critical section
}
```

更稳妥的是使用专用、不可暴露的锁对象。

## `ReentrantLock`

显式锁提供更多控制：

- 可中断获取；
- 尝试获取和超时；
- 可选公平策略；
- 多个 `Condition` 等待队列。

使用时必须在 `finally` 中释放：

```java
lock.lock();
try {
    updateState();
} finally {
    lock.unlock();
}
```

公平锁可以减少长期饥饿，但通常带来额外调度开销。除非业务确实需要等待顺序，不应默认认为公平一定更好。

## `volatile` 的边界

`volatile` 适合表达一个变量的可见状态，例如停止标记。它保证对该变量的读写具有特定内存语义，但不把一组操作合并成原子事务。

```java
count++;
```

包含读取、计算和写入，即使 `count` 是 `volatile`，多个线程仍可能丢失更新。计数场景可以使用原子类或锁。

## CAS 与原子类

原子类通常通过比较并交换完成条件更新：只有当前值仍等于预期值时才写入新值。

CAS 避免了某些互斥等待，但仍要考虑：

- 高竞争下重复自旋；
- ABA 问题；
- 单变量原子操作无法自动维护多变量不变量。

无锁不等于无成本，也不等于所有操作都应该改成 CAS。

## AQS 的角色

许多 JUC 同步器建立在 AbstractQueuedSynchronizer 的状态和等待队列机制上。它把“竞争同步状态”和“获取失败后如何排队、阻塞、唤醒”抽象出来。

理解 AQS 有助于比较 `ReentrantLock`、`Semaphore`、`CountDownLatch` 等工具，但业务代码通常应直接使用这些高层组件，而不是自行实现同步器。

## 线程池的核心参数

线程池设计需要关注：

- 核心线程数；
- 最大线程数；
- 空闲线程存活时间；
- 工作队列；
- 线程工厂；
- 拒绝策略。

任务提交后的行为由“当前线程数、队列是否可接收、是否还能扩容”共同决定。不能只看最大线程数判断并发量。

## 有界队列与背压

无界队列会让生产速度长期高于消费速度的问题表现为内存不断增长。有界队列可以更早暴露过载，并通过拒绝、降级或调用方执行形成背压。

拒绝策略是业务策略，不只是技术参数：

- 丢弃是否允许；
- 是否记录并告警；
- 调用方执行会不会拖垮入口线程；
- 是否可以持久化后重试。

## 如何估算线程数

CPU 密集任务的线程数通常接近可用核心数；大量等待型任务可以更多，但最终仍受下游连接池、队列和内存限制。

比固定公式更可靠的是测量：

- CPU 利用率；
- 任务执行与等待时间；
- 队列长度；
- 拒绝次数；
- 数据库和外部服务并发上限；
- P95/P99 延迟。

线程数超过下游容量只会把等待从一个队列搬到另一个队列。

## 不要在持锁期间做慢操作

临界区应尽量只包含维护不变量所需的步骤。网络调用、磁盘 IO 和不可控回调会延长锁持有时间，并可能形成锁与外部资源之间的死锁。

如果必须先获取数据再修改共享状态，可以把慢操作移出锁，再在进入临界区后重新校验前置条件。

## 诊断并发问题

需要同时观察：

- 线程池活跃数、队列长度和拒绝数；
- 锁等待时间；
- 线程转储中的阻塞关系；
- CPU、上下文切换和系统负载；
- 下游连接池使用量。

只把线程池调大，可能暂时降低队列长度，却让数据库连接和上下文切换更糟。

## 总结

锁维护复合不变量，`volatile` 传递可见状态，原子类优化单变量条件更新，线程池控制任务并发。正确选择依赖实际共享关系和资源上限，而不是把所有并发问题都交给某一个工具。
