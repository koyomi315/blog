# 检查与 Git 发布

发布前读取实际 package.json 和部署工作流，确认现有约定仍适用。当前检查命令是在 blog 中执行 `pnpm check` 和 `pnpm build`。这不是框架开发任务，无需为了纯文档发布查询框架文档；确实遇到版本相关 API 问题时按项目 Context7 约定查证。

1. 修改前记录 blog 工作区与暂存区状态，fetch origin，确认当前分支为 main 且没有待推送的其他提交。远端只领先且工作区干净时可 `git pull --ff-only` 后重新读取受影响的文章；分叉、错误分支或已有本地未推送提交时停下报告，不擅自切换分支、变基或顺带发布他人提交。
2. 已有无关未暂存改动可以保留，但不能覆盖、暂存或提交。暂存区已有改动、本次目标文件已有用户改动，或无法隔离本次范围时停止并说明冲突文件。不要 stash、reset、clean 或强推。
3. 检查最终文章、frontmatter、图片、链接与映射是否一致，检查 diff 中是否仅包含本次预期变化。运行 `pnpm check` 和 `pnpm build`；失败则修复本次引入的问题并重跑。无关的既有失败不顺手修复，也不绕过检查发布。
4. 仅以明确路径暂存本次文章、资源和 `.study-publish-map.json`，不用 `git add .` 或 `git add -A`。核对 staged 文件列表、diff 和 `git diff --cached --check`，确认无其他改动。无内容变化且映射也未变时报告无需发布，不创建空提交。
5. 提交消息使用 `docs: publish <主题>` 或 `docs: update <主题>`。提交后核对该提交仅含本次文件，再执行普通 `git push origin main`。提交失败不推送；推送失败保留本地提交并报告可恢复状态。远端竞态导致拒绝推送时不强推，报告下一步。
6. 推送成功后确认远端 main 包含本次提交。报告文章源路径、目标路径、分类、提交 SHA 和推送结果。推送成功只说明已触发部署；除非实际查到工作流成功，否则不声称网站已上线。站点配置目前包含 example.com，未经核实只给 `/posts/<slug>/` 相对路由。

任何停止都要说明已经完成哪些本地修改、是否已提交、是否已推送，以及具体缺少什么；保留现场供继续，不重复提交已成功的步骤。

## Windows Git 连接排查

本环境 Git 默认使用 OpenSSL；若 GitHub HTTPS 报 TLS unexpected EOF，使用命令级 `-c http.sslBackend=schannel -c http.version=HTTP/1.1` 重试 ls-remote、fetch 或普通 push。这一方式已在本博客发布中验证可用。保持证书验证开启，不改全局 Git 配置；先核对远端状态，再按上述流程提交推送。暂时的连接失败或单次构建失败需重新核实，不据此断言为持续故障。
